# Autonomous procedural visual engine

## Mission
Produce complete visual sequences using original assets generated by deterministic code and composition rather than requiring an external image/video-generation service. This is the default no-provider path.

## What it can create
- SVG/vector illustrations, icons, shapes, diagrams, maps from supplied data, charts, timelines and labels.
- HTML/CSS/Canvas compositions, animated typography, UI mockups, kinetic text, progress bars, counters, transitions and branded layouts.
- 2D characters assembled from original vector parts, simple rigs, pose libraries, facial states and keyframe animation.
- Procedural backgrounds, particles, gradients, geometric patterns, parallax layers, abstract motion, waveform and audio-reactive graphics when audio analysis is available.
- 2.5D scenes from layered original artwork, with simulated camera moves, depth, pan, zoom and compositing.
- Data-driven explainers, educational diagrams, maps and process animations.
- Video assembly from user-supplied footage, licensed local assets or generated-by-code visuals.

## Pipeline
1. Convert brief into a scene graph and style bible.
2. Choose a visual medium per scene (vector, typography, chart, procedural 2D, 2.5D, supplied footage).
3. Generate assets from code using deterministic seeds and reusable components.
4. Animate with frame/time-based keyframes and easing curves; avoid wall-clock-dependent animation.
5. Compose scenes on a common timeline with explicit frame rate, dimensions, safe areas and track hierarchy.
6. Synchronize scene changes, captions, graphics and sound cues to the narration and beat map.
7. Render through a verified local or host-provided runtime.
8. Inspect representative frames, audio and metadata; produce an honest QA report.

## Engine architecture
- Scene graph: nodes, transforms, layers, masks, text, vector paths, images, audio and effects.
- Asset library: reusable original SVG/PNG assets, fonts with licenses, palettes, character rigs and background patterns.
- Animation system: keyframes, easing, paths, camera transforms, opacity, scale, rotation, masks and procedural parameters.
- Compositor: layer order, blend modes where supported, clipping, transitions and safe-area guides.
- Timeline: frame-accurate tracks for visuals, narration, music, ambience, SFX and captions.
- Renderer adapter: use the bundled renderer when verified; keep HyperFrames/FFmpeg adapters optional and capability-checked.
- QA: validate missing assets, frame bounds, overlaps, audio levels, output streams and sample frames.

## Honest capability boundary
This engine can create highly polished motion design, explainers, graphic-led stories, kinetic typography, diagrams, stylized vector animation, procedural scenes and edits of supplied footage. It cannot autonomously invent photorealistic arbitrary footage, realistic humans, real-world locations or complex natural performances at the quality of a dedicated generative video model without such a model or source footage. Do not disguise vector animation as photorealism.

## Timed captions and on-screen text

Use explicit caption text, scene-local start time and duration. In the procedural MP4 renderer, use an element with `type: caption`, `text`, optional `x`, `y`, `size`, `fill`, plus `delay` and `duration`. Caption timing must fit inside its scene. Prefer concise, readable phrases, high contrast and safe-area placement; do not imply word-level karaoke timing unless each word is separately timed. Keep selectable subtitle tracks as a separate accessibility option when supported by the renderer.

## Voice and sound
Use a host-provided speech tool if available, a user recording, or a bundled/local TTS engine only if its executable/model is actually present and licensed. If no voice engine exists, provide a narration script and allow silent or music-only output. Never claim synthesized narration was produced without an actual audio file.

## Portable execution
A Skill package contains instructions and source code; it is not itself a continuously running server. Rendering requires a host that permits code execution and file output. A chat-only host can author the project but cannot run the renderer. The same package should degrade gracefully: generate project source, then render only when a compatible runtime is available.
